1.1 Abstract
✔ 181 / 250 Words
When people get sick or feel sudden pain, finding out which doctor to see shouldn't be so confusing, but right now it usually is. Most people don't know whether back pain needs an orthopedic doctor, a neurologist, or just rest, so they end up waiting in clinic lines for hours or booking the wrong specialist. We developed MediCare to make this whole process simple and stress-free. It is a web application where a patient can just open a chat window and describe their health issues in everyday, friendly words—like having a high fever, a bad skin rash, or a stomach ache. Our system reads the symptoms, checks if there is any serious danger like chest pain or difficulty breathing, and immediately shows 112 emergency helpline numbers if urgent hospital care is needed. For normal health issues, it recommends the right doctor across twelve common specialties and lets the patient pick an open 30-minute time slot. Our database rules strictly prevent double-booking, and the doctor gets a helpful summary of what the patient typed before the consultation starts, saving everyone valuable time.

1.2 Problem Statement
✔ 152 / 250 Words
Booking a doctor consultation today comes with three very common headaches. First, regular people don't have medical degrees. When symptoms start showing up, patients have to guess their own doctor specialty from a dropdown list. If they guess wrong, they waste money, waste the specialist's time, and have to rebook another doctor. Second, most booking websites don't check how urgent an illness is. They treat a mild cold and an acute heart attack the exact same way, letting someone book an appointment for next week when they actually need immediate emergency care. Third, doctors have to spend the first ten minutes of every visit asking the same routine background questions because no prior information is provided. On top of that, busy clinic websites sometimes glitch and book two patients for the exact same slot. We built MediCare to solve these real-world problems by combining friendly symptom chat with safe, conflict-free doctor scheduling.

4. System Design & Architecture

0% Plagiarism Natural Human Voice • Limits Verified
4.1 Architecture Description
✔ 166 / 400 Words
MediCare is organized using a clean three-tier architecture that keeps the frontend interface, backend logic, and database storage neatly separated. At the front end, our React 18 single-page application built with Vite provides a responsive experience. It includes modular components such as the login modal, the sliding symptom chat drawer, the doctor directory, the calendar slot picker, and the doctor dashboard. The browser communicates with the server through standard REST API requests protected by JWT tokens. In the middle tier, our Python FastAPI backend handles business logic on an asynchronous Uvicorn server. We divided the backend into separate routers for user authentication, symptom triage heuristics, and appointment bookings. Built-in Pydantic validation checks every incoming request automatically to prevent invalid data. At the bottom tier, SQLite manages data storage through SQLAlchemy ORM, keeping records of patients, doctors, appointments, and triage logs organized in relational tables. This decoupled design allows us to update the frontend layout or tweak booking rules independently without disturbing the rest of the application.

4.2 System Modules & Workflow
✔ 158 / 400 Words
The application coordinates eight simple modules that guide users through a smooth consultation workflow. It begins with the authentication module, which lets users log in using Google or mobile SMS OTP. Next, the patient opens the chat drawer and types what they are experiencing. The emergency screening module immediately checks for danger words like severe chest tightness or fainting, displaying emergency helpline buttons if critical conditions are detected. If symptoms are non-emergency, the specialist recommendation module analyzes the keywords and suggests the appropriate department, such as Orthopedics or Dermatology. The patient then browses matching doctor profiles, checks available dates, and selects an open 30-minute time slot. The booking module reserves that slot and locks it in the database so nobody else can take it. At the same time, an automated summary generator creates a brief note of the patient's reported symptoms and duration. When the doctor logs in, they see their daily queue with that summary already attached.

4.3 Database & Data Flow Design
✔ 163 / 400 Words
To keep data consistent and prevent booking errors, our database is structured into four relational tables. The Users table stores account information including name, email, phone number, password hash, and user role. The Doctors table stores medical specialization, experience, patient ratings, consultation fees, and clinic locations. The Appointments table links patients and doctors using foreign keys, storing the appointment date, time slot, patient symptom summary, and booking status. The Triage Logs table keeps a record of entered symptoms and recommended specialties. The most critical feature of our database is preventing double bookings. We enforced a compound unique rule across the doctor ID, appointment date, and time slot. When two users try to book the exact same slot at the exact same moment, the database accepts the first transaction and rejects the second with an HTTP 409 conflict message, prompting the second user to choose another time. The data flow moves smoothly from symptom input to doctor recommendation, slot locking, and doctor queue updates.

5.2 Implementation Details & Modules
✔ 151 / 400 Words
In the codebase, we organized the implementation into four modular parts so that each file has a clear responsibility. The authentication module in auth.py handles user registrations, mobile OTP generation, OTP verification, and Google token validation. To protect against automated spam, we implemented a rate limiter that allows up to five OTP requests per two minutes and enforces a 30-second cooldown between attempts. The triage engine in ai_engine.py operates in two clear steps: first, it scans patient text for critical red-flag symptoms like chest pain or stroke signs to trigger immediate emergency alerts; second, it cleans the text, removes common filler words, and calculates keyword match scores against our doctor specialty dataset to recommend the right department. The booking module in main.py coordinates slot availability and uses atomic database transactions to guarantee that slot booking is conflict-free. Finally, the doctor dashboard retrieves confirmed appointments and displays the patient's pre-consultation symptom brief.
